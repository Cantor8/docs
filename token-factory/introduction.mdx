Token Factory issues and operates instruments on Canton. The rules of an instrument live on the ledger. Your services mint, burn, pause, freeze, and monitor through Token App, inside your network. Wallets discover the instrument and prepare transfers through the Registry. The Registry's public API is the internet-facing surface.

The Registry returns choice contexts and does not submit. Wallets submit holder transfers from a public context. Token App submits every admin operation from a context it fetches on the Registry's admin API, which requires M2M authentication. That submission lands on your participant, as a party you control.

You hold every party that can act. Mint, burn, freeze, pause, and activity rewards are authorized by parties you control, on a participant you control. You decide the arrangement: one party or several, and the signing policy behind each key, including a quorum or more than one approver. Cantor8's party is an observer. It can see the instrument. [Roles](/token-factory/roles) is that division of control.

## Who runs what

Default deployment:

| Piece                      | Operator                     | Authority                                                                                       |
| -------------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------- |
| Your participant           | You                          | Hosts the parties you control. Accepts the transactions Token App submits                       |
| Token App and its database | You, on your private network | Fetches a choice context, then submits mint, burn, pause, freeze, and activity markers          |
| Your identity provider     | You                          | Issues credentials for your Ledger API user and for callers of Token App                        |
| Cantor8 participant        | Cantor8                      | Hosts the observer, a read-only party. Hosts a validator only if you ask Cantor8 to operate one |
| Registry                   | Cantor8                      | Reads as the observer. Returns public contexts to wallets and M2M admin contexts to Token App   |
| Registry identity provider | Cantor8                      | Issues the M2M credential Token App uses to fetch admin contexts                                |

You operate the validator, or Cantor8 does if you ask. The parties that mint, burn, pause, and freeze stay yours either way. Those same parties can sit on a private synchronizer. [Architecture](/token-factory/architecture) is the map.

## Terms

<Accordion title="Glossary: ledger, parties, and services" icon="book-open">

| Term               | Meaning                                                                                                                                        |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Participant        | A Canton node. It hosts parties and submits transactions to a synchronizer.                                                                    |
| Party              | An identity on the ledger. Whoever controls its key authorizes what it does.                                                                   |
| Synchronizer       | The domain the participants share: the public Canton synchronizer, or a private one.                                                           |
| Instrument         | One token, with a ticker, name, symbol, and decimal precision.                                                                                 |
| Holding            | A balance of an instrument, owned by a party.                                                                                                  |
| Factory            | The on-ledger contract for one admin. Instruments, transfers, and allocations are created from it.                                             |
| Admin              | The party that creates instruments and controls pause, freeze, and compliance burn.                                                            |
| Issuer             | The party that mints and burns.                                                                                                                |
| Operator           | The party that submits day-to-day mint and burn when that role is separate from the issuer.                                                    |
| Treasury           | The party that holds the standing mint delegation. Issuance to your own books lands here.                                                      |
| Featured-app party | The party that holds the network featured-app right and posts activity markers.                                                                |
| Validator party    | Co-signs the factory. Proposes seizure of funds locked in a pending transfer. The admin approves through Token App.                            |
| Observer           | A party that can see the instrument's contracts and cannot exercise them.                                                                      |
| Holder             | A party that owns a holding.                                                                                                                   |
| DAR                | The compiled suite package. One file is uploaded and vetted.                                                                                   |
| Vetting            | A participant accepts the DAR and will then process transactions that use it.                                                                  |
| Registry           | The service that lists instruments and returns choice contexts. It does not submit transactions.                                               |
| Choice context     | The disclosed contracts and arguments a submitter needs. The Registry returns it. Token App, or the holder's wallet, submits it.               |
| Token App          | Your service that submits admin operations and activity markers, and that stores history, supply, and metrics.                                 |
| Mint delegation    | A recipient's standing consent to receive mints.                                                                                               |
| Activity marker    | A ledger record of qualifying third-party activity, posted by the featured-app party. The network pays beneficiaries from markers.             |
| Beneficiary        | The party credited with an instrument's marker weight.                                                                                         |
| Identity provider  | An OIDC provider. Each connection checks a token that provider issued. Token App and the Registry expect a Keycloak-compatible token endpoint. |

</Accordion>
